# PERF-201 P95 Report

Date: 2026-05-23
Status: In progress

## What was added in this pass

1. `scripts/benchmark-p95.js` now defaults to required PERF-201 endpoints:
   - `/api/products`
   - `/api/chat`
   - `/api/orders`
   - `/api/admin/reports`
2. `scripts/benchmark-p95.js` now fails when any endpoint is unreachable or has zero samples.
3. Added budget evaluator:
   - `scripts/evaluate-p95-budgets.js`
   - `npm run bench:p95:budget`
4. Budget evaluator emits JSON + Markdown artifacts:
   - `docs/evidence/perf-201-budget-*.json`
   - `docs/evidence/perf-201-budget-*.md`
5. `scripts/benchmark-p95.js` now supports endpoint-specific override matrix via `BENCH_ENDPOINT_MATRIX_JSON`:
   - per-endpoint `method`
   - per-endpoint `headers`
   - per-endpoint `body`
   - per-endpoint `allowStatuses`
   - per-endpoint `successStatuses`
6. Benchmark results now distinguish all-response latency (`p95`) from success-path latency (`successP95`), and fail when an endpoint only returns auth failures or disallowed statuses.
7. Added reusable matrix template: `docs/perf-endpoint-matrix.example.json`.
8. Added matrix renderer: `npm run bench:p95:matrix` generates a local matrix file from `BENCH_BUYER_COOKIE` and `BENCH_ADMIN_COOKIE`.
9. Added local orchestrator: `npm run bench:p95:local` runs matrix render -> benchmark -> budget evaluation and stores a local summary artifact.

## Observed results

1. `/api/chat`, `/api/orders`, `/api/admin/reports` produced low p95 values in these runs (fast `401` responses).
2. `/api/products` was unreachable/timeouts (0 samples, 100% errors), causing budget failure.
3. A direct probe on 2026-05-23 confirmed `/api/products` timeout in current local runtime.
4. These runs are now explicitly considered non-meaningful for PERF-201 because they do not exercise authenticated success paths.

## Why PERF-201 is still blocked

1. Current local runtime is not DB-ready for `/api/products` benchmark flow.
2. The benchmark currently captures auth-failure latencies (`401`) for protected endpoints, which are not representative of seeded business-path performance.
3. Baseline-like vs hardened comparison requires stable seeded data and comparable auth context; that is not available in this local run.

## Next run requirements to close PERF-201

1. Start app against seeded, stable DB state.
2. Provide authenticated context (cookie/token) where needed for representative endpoint behavior.
3. Provide endpoint-specific benchmark matrix so protected routes assert `200` success-path latency instead of auth-failure latency.
4. Run benchmark twice (baseline-like and hardened) with same dataset and load profile.
5. Re-evaluate budgets and include `successP95`/error-rate interpretation in final report.

## Ready-to-run command templates

1. Baseline-like capture:

```bash
node scripts/benchmark-p95.js \
  --base=http://127.0.0.1:5000 \
  --endpoints=/api/products,/api/chat,/api/orders,/api/admin/reports \
  --requests=40 \
  --concurrency=8 \
  --timeout=5000 \
  --warmup=3 \
  --header=authorization:Bearer <token>
```

2. Hardened capture (same dataset and auth context):

```bash
node scripts/benchmark-p95.js \
  --base=http://127.0.0.1:5000 \
  --endpoints=/api/products,/api/chat,/api/orders,/api/admin/reports \
  --requests=40 \
  --concurrency=8 \
  --timeout=5000 \
  --warmup=3 \
  --header=authorization:Bearer <token>
```

3. Authenticated matrix example:

```json
{
  "/api/products": {
    "method": "GET",
    "allowStatuses": ["200"],
    "successStatuses": ["200"]
  },
  "/api/orders": {
    "method": "GET",
    "headers": {
      "cookie": "token=<jwt>; csrf=<csrf>"
    },
    "allowStatuses": ["200"],
    "successStatuses": ["200"]
  },
  "/api/admin/reports": {
    "method": "GET",
    "headers": {
      "cookie": "token=<admin_jwt>; csrf=<csrf>"
    },
    "allowStatuses": ["200"],
    "successStatuses": ["200"]
  }
}
```

4. Budget evaluation:

```bash
node scripts/evaluate-p95-budgets.js --baseline=<baseline-json> --current=<current-json>
```

5. Local one-shot run:

```bash
npm run bench:p95:local
```

Notes:
1. `scripts/benchmark-p95.js` now supports `BENCH_HEADERS_JSON`, `BENCH_AUTH_BEARER`, and `BENCH_COOKIE`.
2. `BENCH_ENDPOINT_MATRIX_JSON` or `BENCH_ENDPOINT_MATRIX_FILE` should be used whenever different endpoints require different auth/body semantics.
3. Start from `docs/perf-endpoint-matrix.example.json` or generate `docs/perf-endpoint-matrix.local.json` via `npm run bench:p95:matrix`.
4. Set `BENCH_BUYER_COOKIE` and `BENCH_ADMIN_COOKIE` before running the matrix renderer.
5. Optional: set `BENCH_BASELINE_ARTIFACT` before `npm run bench:p95:local` to compare against an earlier benchmark artifact.
6. Keep benchmark auth and seed state identical between baseline/current runs.
